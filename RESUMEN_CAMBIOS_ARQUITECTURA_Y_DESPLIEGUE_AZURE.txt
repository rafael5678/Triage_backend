1. RESUMEN EJECUTIVO PARA CURSOR: QUÉ PASÓ Y EN QUÉ ESTADO ESTAMOS
--------------------------------------------------------------------------------
- El proyecto TriageIA (Sistema de Triaje Hospitalario Inteligente) completó su
  migración de arquitectura monolítica a MICROSERVICIOS REALES INDEPENDIENTES.
- EL MONOLITO (`legacy-monolith/`) HA SIDO ELIMINADO DEFINITIVAMENTE del código
  activo. NO EXISTE ni debe volver a crearse.
- Se eliminaron configuraciones y scripts obsoletos de plataformas que no usamos
  (Google Cloud Run: `deploy/cloudrun.sh` y `docs/DEPLOYMENT_CLOUD_RUN.md`).
- El backend consta ahora de 7 módulos Maven:
  * 1 API Gateway reactivo (Spring Cloud Gateway en puerto 8080).
  * 4 Microservicios de dominio (Spring Boot en puertos 8081, 8082, 8083 y 8084).
  * 2 Módulos de contratos compartidos (Java común y gRPC / Protobuf).
- La infraestructura en Microsoft Azure (`triage-brazilsouth` en `brazilsouth`)
  SE CONSERVA AL 100% y se le incorporó el API Gateway como punto de entrada público.
- La base de datos es Supabase PostgreSQL (Postgres 15+, Session Pooler con SSL).
- El frontend está en Vercel (React + Vite) y consume la API a través del Gateway
  sin haber cambiado una sola línea de código en React.

3. MATRIZ DE MICROSERVICIOS, PUERTOS Y RESPONSABILIDADES
--------------------------------------------------------------------------------

1. api-gateway (Puerto 8080):
   - Tecnologías: Spring Boot 3.3.4, Spring Cloud Gateway 2023.0.3, Netty reactivo.
   - Es el ÚNICO punto de entrada público expuesto al exterior en Azure e Internet.
   - Centraliza CORS para el frontend de Vercel y localhost.
   - Enrutamiento:
     * /api/v1/auth/** y /api/v1/admin/users/** -> ms-pacientes-auth (:8081)
     * /api/v1/triage/patients (POST)          -> ms-pacientes-auth (:8081)
     * /api/v1/triage/patients (GET)           -> ms-cola-espera (:8083)
     * /api/v1/triage/evaluations/**           -> ms-evaluacion-triaje (:8082)
     * /api/v1/triage/analyze                  -> ms-evaluacion-triaje (:8082)
     * /api/v1/triage/patients/*/history       -> ms-evaluacion-triaje (:8082)
     * /api/v1/triage/care/**                  -> ms-cola-espera (:8083)
     * /api/v1/triage/events (SSE streaming)   -> ms-cola-espera (:8083)
     * /api/v1/triage/stats, board, health     -> ms-cola-espera (:8083)
     * /api/v1/ia/**                           -> ms-ia-recomendacion (:8084)
     * /api/v1/catalog/**                      -> ms-ia-recomendacion (:8084)
     * /api/v1/admin/symptoms/**               -> ms-ia-recomendacion (:8084)

2. ms-pacientes-auth (Puerto 8081):
   - Responsabilidad: Ficha demográfica del paciente, autenticación JWT/BCrypt y
     gestión de usuarios (ADMIN, MEDICO, ENFERMERO).
   - Base de Datos: Dueño de las tablas `pacientes` y `app_users`.
   - gRPC: Expone servicio `PatientLookup` sobre HTTP/2 h2c en el mismo puerto 8081.

3. ms-evaluacion-triaje (Puerto 8082):
   - Responsabilidad: Motor de cálculo clínico de gravedad. Implementa NEWS2,
     Manchester, reglas pediátricas por edad y alertas obstétricas (preeclampsia/shock).
   - Historial de reevaluaciones de signos vitales.
   - Base de Datos: Dueño de `signos_vitales` y `evaluaciones_triage`.
   - gRPC: Consume `PatientLookup` de pacientes y `ClinicalAi` de IA. Expone
     `EvaluationAccess` para la cola de espera.

4. ms-cola-espera (Puerto 8083):
   - Responsabilidad: Gestión de la sala de espera priorizada en memoria concurrente.
   - Emisión de Server-Sent Events (SSE) en `/api/v1/triage/events` para actualización
     en vivo del tablero de urgencias. Notificaciones WhatsApp de turno.
   - Base de Datos: Stateless (no persiste en base de datos; delega el estado clínico
     a ms-evaluacion-triaje mediante gRPC).

5. ms-ia-recomendacion (Puerto 8084):
   - Responsabilidad: Análisis clínico asistido con Google Gemini Flash.
   - Ingesta de relato clínico (voz/texto), extracción de signos y sugerencias diagnósticas.
   - Resiliencia y Fallback:
     * Si Gemini responde HTTP 503 (sobrecargado) o 429 (límite alcanzado), conmuta
       automáticamente al modelo de respaldo (`gemini-1.5-flash` -> `gemini-2.0-flash`).
     * Control de cuota diario (150 llamadas) persistido en tabla `gemini_usage_audit`.
     * Caché en memoria (TTL 30 min) para consultas repetidas.
     * Si la IA no está disponible o se agota la cuota, activa degradación elegante
       hacia las reglas clínicas por protocolo sin arrojar error al médico.
   - Base de Datos: Dueño de `symptoms` y `gemini_usage_audit`.

6. triage-common-contracts:
   - DTOs compartidos (`IntakeRequest`, `RankedPatientDTO`, `BoardEntryDTO`), enums
     clínicos (`TriageLevel`, `CareArea`, `CareStatus`) y excepciones de dominio.

7. triage-grpc-contracts:
   - Definición `triage.proto` y stubs compilados de gRPC para comunicación entre servicios.

4. INFRAESTRUCTURA Y DESPLIEGUE EN MICROSOFT AZURE
--------------------------------------------------------------------------------

A. Parámetros del Entorno de Azure:
- Resource Group: `triage-brazilsouth`
- Región: `brazilsouth`
- Plataforma: Azure Container Apps (ACA)
- Entorno ACA: `triage-grpc` (Modo WorkloadProfiles / Consumption)
- Container Apps activas:
  1. `ms-pacientes-auth`
  2. `ms-ia-recomendacion`
  3. `ms-evaluacion-triaje`
  4. `ms-cola-espera`
  5. `api-gateway` (nuevo punto de entrada público)

B. Imagen Docker en GitHub Container Registry (GHCR):
- Repositorio de imagen: `ghcr.io/rafael5678/triage-backend:latest`
- El Dockerfile raíz es multi-stage y compila los 5 JARs ejecutables.
- Cada contenedor en Azure levanta su servicio específico configurando la variable:
  `MODULE=api-gateway`
  `MODULE=ms-pacientes-auth`
  `MODULE=ms-ia-recomendacion`
  `MODULE=ms-evaluacion-triaje`
  `MODULE=ms-cola-espera`
- Cuando se hace push a `develop` o `main`, GitHub Actions (`imagen.yml`) compila
  y sube automáticamente la imagen a GHCR.

C. Conexión con Supabase PostgreSQL:
- Se conecta mediante **Supabase Session Pooler** (puerto 5432 o 6543) con SSL obligatorio.
- Variable inyectada como secreto: `DATABASE_URL=secretref:dburl`
- Evita problemas de resolución IPv6 que ocurren en Azure Container Apps al usar conexión directa.

D. Explicación del Error 'az ad sp create-for-rbac' (Azure for Students):
- En cuentas universitarias de Microsoft Entra ID (Azure AD), los estudiantes no tienen
  permiso de administrador para registrar aplicaciones de directorio.
- Por tanto, `az ad sp create-for-rbac` falla con: *"Insufficient privileges to complete the operation"*.
- SOLUCIÓN ESTABLE: El despliegue y actualización se realizan directamente desde
  **Azure Cloud Shell (Bash)** en el navegador (`portal.azure.com`). Cloud Shell hereda
  la identidad autenticada con permisos de Contributor sobre `triage-brazilsouth` sin
  necesitar ningún Service Principal.

5. COMANDOS OFICIALES PARA AZURE CLOUD SHELL (BASH)
--------------------------------------------------------------------------------

A. Despliegue Completo Inicial o Reconfiguración:
En Azure Cloud Shell:
```bash
cd ~/Triage_backend 2>/dev/null || git clone https://github.com/rafael5678/Triage_backend.git ~/Triage_backend
cd ~/Triage_backend
git fetch origin
git checkout main
git pull origin main

LOCATION=brazilsouth RG=triage-brazilsouth bash deploy/azure.sh
```
(El script es idempotente: comprueba recursos existentes, actualiza las 4 apps de
dominio y crea/actualiza `api-gateway` con Ingress externo en puerto 8080).

B. Actualización Rápida de los 5 Contenedores (Tras nuevo push a GitHub):
```bash
for app in ms-pacientes-auth ms-ia-recomendacion ms-evaluacion-triaje ms-cola-espera api-gateway; do
  echo "== Actualizando $app =="
  az containerapp update -n "$app" -g triage-brazilsouth \
    --image ghcr.io/rafael5678/triage-backend:latest \
    --revision-suffix "r$(date +%s)" -o none
done
```

C. Monitoreo de Logs en Vivo:
```bash
# Logs del API Gateway
az containerapp logs show -n api-gateway -g triage-brazilsouth --type console --tail 40 --format text

# Logs de Pacientes / Auth
az containerapp logs show -n ms-pacientes-auth -g triage-brazilsouth --type console --tail 40 --format text

# Logs de Evaluación
az containerapp logs show -n ms-evaluacion-triaje -g triage-brazilsouth --type console --tail 40 --format text
```

6. CONEXIÓN DEL FRONTEND EN VERCEL (CERO CAMBIOS EN REACT)
--------------------------------------------------------------------------------
El frontend (`Triage_frotend-`) consume las APIs mediante 4 variables de entorno.
Una vez obtenido el FQDN público del Gateway (ej: `api-gateway.whitemushroom-c888e1de.brazilsouth.azurecontainerapps.io`),
se configuran en Vercel (`Project Settings -> Environment Variables`):

```env
VITE_AUTH_URL=https://<FQDN_API_GATEWAY>
VITE_EVAL_URL=https://<FQDN_API_GATEWAY>
VITE_QUEUE_URL=https://<FQDN_API_GATEWAY>
VITE_AI_URL=https://<FQDN_API_GATEWAY>
```
Y se hace clic en **Redeploy**. NO SE TOCA EL CÓDIGO EN `src/services/api.js`.
